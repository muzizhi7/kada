# 本地长任务 Agent — 产品与实现 Spec

> 历史归档：保留原型实验和曾经讨论过的方向，不作为当前实施清单。当前产品范围以仓库根目录 `SPEC.md` 为准，尤其遵守不重复建设 Agent infra 的约束。

版本：0.2 · 2026-10-30

## 1. 目标与判断标准

用户给出目标后，Agent 在本地持续工作，调用线上模型，必要时委派子 Agent，最终交付可检查的结果。退出聊天不停止任务；进程退出后能从持久状态继续。遇到缺少信息、权限或预算时，准确说明原因和下一步。

第一优先级是完成真实工作。项目发布、名称、社区运营和漂亮界面均在效果验证之后。本 Spec 沿用已经选定的 Pi，不更换底层框架。

“长任务”指需要多步执行、状态积累、失败恢复和结果检查的目标，不以运行时长或模型调用次数作为成功依据。电脑休眠或关机时不能执行；恢复后继续不等于离线时仍在工作。

## 2. 基线与缺口

已有：终端多轮聊天、独立后台服务、多供应商模型接入、Pi SQLite 会话恢复、并行子会话、工作区文件工具、时限控制、stdio MCP 电脑工具桥接。

缺口：主 Agent 的最终答复被直接视为完成；计划和验收条件没有独立状态；没有宿主监督与返工；电脑调用只有单次串行，没有整段流程占用；子 Agent 仍是等待整批结束的委派工具。真实桌面流程尚未联调。

## 3. 第一阶段 M1：目标、监督、验收闭环

本轮实现 M1，保留终端入口和现有委派方式。先用文件分析与报告任务验证闭环。真实桌面执行和可长期交互的子 Agent 分别在 M2、M3 验收，不能用模拟测试替代它们的实际完成。

### 3.1 用户入口

- 自然语言创建任务；原有聊天、后台运行、追加消息、暂停、恢复、取消继续可用。
- API/CLI 可以额外提供可执行验收条件。未提供时，主 Agent 制定计划并补充检查项；用户不必手写 JSON 才能使用。
- 用户追加要求后产生新目标修订，原交付不再代表新要求已经完成；同一 request ID 的重发不能重复修订或执行。
- 状态中展示目标、计划、交付路径、检查结果、返工次数、阻塞原因和最近事件。待验收的答复不能在终端显示为已完成。

### 3.2 持久任务状态

`task.json` 保存身份、原始目标、模型、工作区和预算配置；Pi session document 保存不断更新的目标状态。工作进度不依赖模型还能否在上下文中找到旧消息。

目标状态至少包含：

- 目标修订及用户补充要求；
- 有稳定 ID 的计划步骤、步骤状态和简要证据；
- 验收条件及来源（用户或 Agent）；
- 候选交付：摘要、产物路径、候选 ID；
- 机械检查结果、产物内容摘要哈希、独立评审结果；
- 返工次数、连续无进展次数、最后处理的模型提交；
- 待投递消息及固定 request ID；
- 阻塞原因、待回答问题和有界事件记录。

阶段状态与用户控制状态分开保存：

| 对外状态 | 含义 | 继续条件 |
|---|---|---|
| pending / running | 等待执行或正在推进 | 自动 |
| verifying | 已提交候选，宿主正在检查 | 自动 |
| completed | 当前修订通过检查和独立评审 | 用户追加要求时重新执行 |
| waiting_user | 缺少用户信息，保存具体问题 | 用户回答 |
| blocked | 外部依赖不可用，保存原因 | 用户补充信息或显式恢复 |
| needs_attention | 返工或无进展达到上限 | 用户调整目标或显式恢复 |
| failed | 本轮执行未能得到有效结果 | 显式恢复或补充消息 |
| paused | 用户暂停 | 显式恢复 |
| budget_limited | 时间或模型 token 预算耗尽 | 显式恢复，补充一份预算 |
| cancelled | 用户取消 | 不可恢复，需新建任务 |
| answered | 旧版本任务只得到模型答复 | 不表示已通过新验收 |

旧任务不自动重新执行，也不追认已通过新验收。新任务使用版本标记启用监督机制。

### 3.3 主 Agent 协议

提供以下持久工具，仅主 Agent 可以使用：

1. `task_plan`：记录/调整步骤，追加可执行检查。已有检查只能保留或加强，不能由 Agent 删除或降低用户要求。
2. `task_checkpoint`：记录步骤状态、已完成工作和证据。
3. `task_status`：读取当前目标与监督状态。
4. `task_submit`：提交交付摘要与路径，并让出执行权。工具成功只表示候选已登记。
5. `task_blocked`：记录原因，可附必须由用户回答的问题；停止自动续跑。

状态写入工具只返回简短确认，详细目标状态通过 `task_status` 按需读取。不可在每次进度更新时回传整个状态和事件历史，避免上下文重复膨胀。

主 Agent 直接说“完成”而未提交时，监督器发送协议提示；重复不遵循协议最终进入 `needs_attention`，不能无限自循环。

### 3.4 独立验收

先由宿主代码重新读取真实文件，运行声明的检查，再让一个新上下文的评审会话检查原始目标、用户补充要求、候选和产物。

M1 支持文本产物（单个文件不超过 1 MiB）：

- `file_exists`：工作区内存在可读普通文件；
- `file_contains`：文件包含指定文本；
- `json_value`：JSON Pointer 指向的值与指定标量严格相等；
- 所有声明交付的文件都必须存在、非空，记录 SHA-256；
- 有计划时，提交前所有计划步骤应已完成。

不能配置任意 Shell/JavaScript 作为验收条件。路径沿用工作区防越界和防符号链接约束。用户提供的检查在创建时固定；Agent 补充的检查只追加。自由文本答复可以没有文件，但仍需提交并通过独立评审。

评审会话只提供读取文件、列目录和提交评审意见的工具，不提供写入、委派、修改目标或电脑操作。评审必须对照目标，而非照抄主 Agent 的“完成”声明。通过前再次读取产物；评审期间发生修改须重新验收。评审会话身份和投递 ID 持久化，重启复用同一评审。

机械检查通过能证明已声明的条件成立；模型评审提供语义质量检查，仍可能误判。不得声称它能证明报告事实完全正确。M2 的真实场景用独立人工抽查补充评价。

### 3.5 监督器

监督器在模型循环之外运行，后台无需客户端轮询也能工作：

1. 等 Pi 当前工作到达空闲边界；
2. 若明确阻塞，保存状态并等待；
3. 若无候选，要求主 Agent 补全提交协议；
4. 若有候选，运行机械检查和隔离评审；
5. 不合格时，将具体失败证据送回主 Agent，要求修正；
6. 合格时将当前修订标记为完成；
7. 返工耗尽或连续无实质进展时停止，保留最后问题。

默认最多自动返工 3 次、连续相同进展指纹最多 2 次。进展指纹使用计划步骤状态与实际产物/检查结果，单纯改写总结、时间戳或进度备注不算进展。模型单轮内无限操作仍由任务总时限和 token 预算限制。

默认总时限 1 小时，总模型 token 配额 500,000。token 消耗累计主 Agent、子 Agent、评审和上下文压缩，由 Pi 的 usage ledger 提供。定期检查预算；并发在途请求可能超额，属于软上限。供应商缺失或不准确的 usage 不能当作精确计费。重启不补预算；显式恢复增加一份配置的时间和 token 配额，并清零本次监督重试计数，已用量保留。

### 3.6 恢复与副作用

- 监督决定与待投递消息在同一 Pi 事务中保存。先持久化、后投递；恢复时复用 request ID，避免重复续跑。
- 候选、评审身份、评审结论、返工次数、验收记录在重启后仍然存在。
- 暂停关闭执行实例，不把任务当完成。取消须停止同库内的主任务、子 Agent 和独立评审。
- 文件写入与桌面动作保持不可自动重放；中断后先读实际状态。
- 不承诺第三方 UI 操作 exactly-once；恢复数据库不等于恢复外部应用到历史画面。

## 4. 第二阶段 M2：真实电脑工作流

接通一个真实本地桌面驱动，首个平台为当前开发环境 macOS。安装和系统授权完成后才能宣称真实电脑能力可用。

- 保留 MCP 接口和显式工具 allowlist，按驱动规则加载必要操作说明。
- 桌面按整段工作流租用：获取 → 观察 → 操作 → 再观察/验证 → 释放；多个任务不能交错抢焦点。
- 租约需要超时、取消和崩溃释放；重获后重新观察，不继续使用旧截图坐标。
- 检测用户接管或需要登录/系统权限时，转入明确的用户等待状态。
- 文件/API/浏览器结构化接口可完成的步骤优先使用对应接口，需要 GUI 才用屏幕操作。
- 首个真实流程：读取本地资料 → 两个子 Agent 独立分析 → 浏览器补充来源 → 形成报告及附件 → 重新打开和检查交付。
- 先让人工检查最终内容，再衡量减少介入的效果。

## 5. 第三阶段 M3：持续子 Agent 协作

现有 `delegate` 整批等待保留。再增加持久的 spawn / status / message / wait / stop：

- 每个子任务有目标、验收条件、工作目录、预算、交付和失败原因；
- 父 Agent 可以继续其他工作、补充指令、重试单个失败任务；
- 子 Agent 通过消息交接，有固定投递 ID，不能仅靠共享聊天历史；
- 子 Agent 不默认获得桌面控制权；
- 并发数有上限，避免无限递归和放大成本；
- 子 Agent 报告完成后，父任务仍需验收结果。

## 6. 架构与接口

```text
终端聊天 / CLI / 本地 HTTP API
              ↓
LocalRuntime：控制、恢复、预算、监督
              ↓
GoalDoc：目标修订、计划、候选、验收、消息 outbox
              ↓
Pi durable：模型循环、工具任务、压缩、子会话、SQLite
    ├─ Pi AI → 在线模型
    ├─ 工作区工具 → 本地产物
    ├─ 只读评审会话 → 独立意见
    └─ MCP → 电脑驱动（M2 真实验收）
```

沿用 `/v1/tasks` 和控制接口。创建任务增加可选 `acceptance` 数组；查询增加 `goal` 和实际执行 `status`；任务列表展示真实状态。CLI `run` 增加 `--acceptance <JSON 文件>`。聊天 `/status` 展示计划进度、检查与阻塞原因。

任务控制与监督更新串行化；耗时模型请求不在宿主串行锁中等待。API 监听 loopback、token 认证、跨源拒绝和单进程存储锁维持原有约束。

## 7. 验证与发布门槛

M1 必须覆盖：

| 编号 | 场景 | 必须观察到的结果 |
|---|---|---|
| A1 | 模型未交付就声称完成 | 不标完成，自动要求提交，重复时有界停止 |
| A2 | 缺文件或 JSON 数值错误 | 宿主给出具体错误，修正后才进入评审 |
| A3 | 格式正确但漏掉用户要求 | 只读评审拒绝，主 Agent 返工 |
| A4 | 交付、检查、评审均通过 | completed，保留文件哈希与评审证据 |
| A5 | 相同失败反复出现 | needs_attention，无无限续跑 |
| A6 | 评审或返工边界发生 SIGKILL | 身份、预算、计数与投递不重复 |
| A7 | 暂停/取消时有子任务或评审 | 不再推进，恢复语义符合控制状态 |
| A8 | 缺用户信息 | waiting_user，回答后继续同一任务 |
| A9 | 时间/token 超限与重启 | budget_limited，重启不自动补额度 |
| A10 | 完成后追加要求及重复投递 | 仅新要求触发一轮新验收，同 ID 不重复 |

自动测试使用显式模拟模型和桌面；另保留线上模型的小规模联调记录。阶段效果记录必须区分离线测试、线上模型文件任务和真实电脑任务。

公开发布前的目标：固定 10 个真实案例，覆盖材料整理、计算校验、研究报告和跨应用流程；同一预算及验收标准下至少 8 个完成；专门注入断网、进程强杀、子 Agent 失败与页面变化。记录成功率、人工介入次数、时长、usage 和失败原因。该比例是未来门槛，不是当前成绩，也不是对任意任务的承诺。

## 9. v0.3 修订草案：连续执行、联网证据与成本管理

状态：2026-10-30 根据真实报告任务和公开方案调研补充，尚未在运行时代码中实现。本节提出的预算行为将取代 3.5 节中 v0.2 的累计 token 分段暂停；v0.2 实现与验证记录继续保留。

### 9.1 用户目标与真实缺口

用户给定目标和已有配置后，Agent 应在已授权的任务范围及总预算内持续推进，自行处理上下文压缩、阶段交接、常规重试、子任务调整和验收返工。上下文整理、内部执行轮次结束、累计 token 跨过某个统计值，不是要求用户发送“继续”的理由。

真实案例：任务 `eab55c0a-123f-4929-a560-87e167a79a0a` 运行 5 个子 Agent 和一个评审，累计 1,172,657 token（其中缓存读取 910,720、普通输入 196,781、输出 65,156）。用户两次 `/resume` 才完成。主 Agent 记录到的单次最大输入约 77,007 token，远未达到模型窗口。

本地 Pi 1.4.0 默认策略为：`reserveTokens=16384`、`backgroundTokens=32768`、`keepRecentTokens=20000`。对目录中 1,000,000 token 的模型，后台压缩触发点约 950,848；当前 500,000 的全任务累计停止线会先触发。这不是上下文已满，而是宿主预算与工作上下文策略不匹配。

该报告还声明“未联网”，却通过了用户“查资料”的要求：文件与格式通过检查，不能证明资料实际查证过。v0.3 必须修复这一完成判定缺口。

### 9.2 参考方案与取舍

以下是针对本项目的参考优先级，不是统一基准下的全球性能排名。保留 Pi 与多供应商选择，不因调研而切换框架。

| 参考 | 公开方案提供的思路 | 本项目采用方向 |
|---|---|---|
| [Anthropic：长任务 Harness](https://www.anthropic.com/research/harness-design-long-running-apps) | 分解任务、结构化交接、规划/执行/评审分离；压缩与重置各有代价 | 让阶段结果和下一步成为可恢复状态，按需要交接，不机械清空上下文 |
| [Claude Managed Agents](https://www.anthropic.com/research/managed-agents) | 会话日志、Harness、执行环境分离，历史可重新检索 | 长期任务不绑定某一个模型上下文，执行器失败与模型上下文丢失分别恢复 |
| [OpenAI Agents API](https://developers.openai.com/api/docs/guides/agents-api/overview) | 持久会话、上下文管理、子 Agent 与恢复由运行时负责 | 将这些行为放在宿主层，而不是让用户逐轮继续；托管产品作为对标 |
| [Manus：Context Engineering](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus) | 稳定缓存前缀、文件保存大量材料、保留可回读的引用 | 原文和长产物落盘，模型按需取片段；同时观察缓存命中和每个完成任务的成本 |
| [Deep Agents：Context Engineering](https://docs.langchain.com/oss/javascript/deepagents/context-engineering) | 大工具输入/输出外置、自动总结、子 Agent 独立上下文 | 优先借鉴可复用的开源实现，处理写文件参数与读文件结果在历史中重复堆积的问题 |
| [Temporal：Agent memory and state](https://docs.temporal.io/ai/featured/memory-state-stripe) | 区分上下文、记忆、执行位置和外部动作是否生效 | 保持持久执行状态和幂等交接；本地首版不额外引入服务集群 |

### 9.3 联网接入

默认优先使用当前模型供应商的官方联网能力。对当前 DeepSeek Flash，已经用本机现有 Key 测试：

- `POST /v1/tools/search` 返回 HTTP 200 与 3 条结果；
- `POST /v1/tools/fetch` 对 DeepSeek 文档返回 HTTP 200、9,406 字符正文；
- 对一个 Anthropic 页面抓取返回 404。单站抓取失败不代表账号没有联网能力，需要区分失败原因并选择可用的普通正文读取渠道。

来源：[DeepSeek Search & Fetch 官方接口](https://api-docs.deepseek.com/guides/search/)。接口测试记录保存在忽略目录 `.harness/research/2026-10-30/`，不包含 Key。

当前 [Responses 兼容文档](https://api-docs.deepseek.com/guides/responses_api/) 将服务端内置 `web_search` 标为 Pro 支持、Flash 忽略。因此不能只在现有 Flash 请求中添加该字段就认为搜索生效。v0.3 先将官方 Search/Fetch 接入 Pi 工具层，由模型自主调用，并以真实回执确认执行。

Agent Reach 的 skill 和命令在本机已经存在；它不会自动出现在项目的 Pi 工具列表中。增加按需加载的 skill 和只读渠道适配，补充普通正文读取、GitHub、中文平台、字幕等能力。参考 [Agent Reach 官方仓库](https://github.com/Panniantong/Agent-Reach)。只暴露结构化、允许范围内的查询和读取，不为使用 skill 顺带开放任意 Shell。需要登录的渠道保留用户本人完成登录的入口。

统一的联网结果应保留来源 URL、标题、发布/获取时间、正文存储位置、正文哈希和所用渠道。检索摘要与已读正文分开标记。缓存正文和重复查询，避免多个子 Agent 重复抓取同一内容。

### 9.4 自动执行与预算

预算分为三种，不能再用同一个累计 token 数混用：

1. 工作上下文容量：达到软阈值时外置大内容、保留交接信息并自动压缩，随后继续原目标。阈值由模型与任务评估配置，不照搬理论最大窗口。
2. 全任务资源上限：来自本地默认配置或用户事先设置的总费用、总时长与执行次数。累计计入主 Agent、子 Agent、评审、压缩和搜索费用。达到真实硬上限才进入 `budget_limited`，不在后台擅自追加费用额度。
3. 异常保护：记录重复失败和没有改善的尝试，触发诊断、换方案、缩小子任务或重新委派；恢复策略耗尽才说明无法继续。避免消耗预算却不增加可验证进展。

缓存读取、未缓存输入、输出、压缩和搜索费用分别统计。费用采用供应商可验证用量与明确标注的价格估算，不能把估算冒充真实账单；未知价格需要保守的备用上限。公开状态中展示每个子任务、每个阶段的估算消耗、剩余预算和停止原因。配置一次预算即可使用，不在每段内部执行前重复提问。

普通超时和可重试限流按有界退避处理；可用后自动恢复。阶段完成、压缩和重试只更新进度，不要求用户回复。只有必须补充的信息、身份认证/实际授权、真正用尽的总预算或无法继续的外部阻塞需要用户介入。

### 9.5 控制上下文重复与子任务成本

- 长网页、资料正文、长 `write_file` 参数及已写入的报告正文，持久保存后可从活动上下文中替换成可回读引用；保留原始日志，不静默丢失证据。
- 文件读取增加按段/按行读取与检索，避免为了一个数字反复回读整份报告。
- 子 Agent 返回简短摘要、关键结论、证据 ID、交付路径和未解决问题，完整研究记录留在各自目录。父 Agent 按需取细节，不接收全部研究过程。
- 独立任务并行，相关任务复用已有结果。并行数有上限，完成任务数与同时运行数分别显示。
- 评审按验收项定位相关段落和来源；变更后优先复核受影响内容，最终仍检查交付是否满足完整目标。
- 固定的系统前缀与工具 schema 尽量稳定；压缩本身会改变后续缓存，应以正确率和每个完成任务的成本评估收益，不把缓存命中率当作唯一目标。

### 9.6 研究任务验收与下一次实测

“查资料”是任务要求时，完成条件须包含宿主记录的真实搜索/正文读取回执与对应引用；模型不能通过写一句“离线环境，仅供参考”将此要求降级。关键事实需要能追溯到可读取的来源；预测需区分于来源已证实的事实。搜索失败要记录未完成部分，不能自动转成离线写作后照常通过。

先用同一个汽车行业 2027 展望案例回归，固定评价标准：

- 用户仅提交目标一次，在事先给定的总预算内，不发送 `/resume` 仍能完成；
- 联网回执和引用真实存在，关键取数能追溯到正文；
- 至少演练一次上下文压缩或阶段交接，目标与证据不丢失；
- 注入网络超时和子 Agent 失败，能自行恢复或报告准确的实际阻塞；
- 完成率与正确性不低于现有版本，同时记录每阶段成本、总耗时、重复抓取与人工介入次数；
- 单独验证真实硬预算会生效，自动续跑不会绕开上限。

实施顺序：先完成官方联网工具与证据验收、上下文外置/自动压缩、费用预算与自主恢复，再继续整段桌面流程租约和完整的异步子 Agent 消息能力。此顺序调整不改变本地长任务这一项目方向。
