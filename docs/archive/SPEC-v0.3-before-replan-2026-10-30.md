# 本地长任务扩展 — 产品与实现 Spec

范围确认：2026-10-30。当前代码为 v0.3.0 首轮实现；本文同时规定产品边界与后续验收目标，已验证范围见第 8 节。

## 1. 定位

一个基于 Pi 的轻量开源扩展，让 Agent 在本地通过终端、文件工具和现成的 computer-use 驱动，持续完成需要多步执行的复杂任务。

项目负责应用层的长任务推进策略与本地执行衔接。模型接入、Agent 循环、会话、工具执行、压缩、持久化和基础恢复由 Pi 提供。不建设 Agent infra，不实现第二套运行时。

用户给出一次目标后，Agent 在已有配置和任务预算内持续推进。阶段交接、上下文整理和常规重试不要求用户再发“继续”。完成、必须补充信息、真实外部阻塞或总预算确实耗尽时，给出明确结果与原因。

## 2. Pi 与本项目的能力边界

以下按当前安装的 Pi 1.4.0 核对；接入新能力前检查该版本的公开 API 与原生工具。

| 能力 | 优先复用 | 本项目只补充 |
|---|---|---|
| 模型与多供应商 | Pi AI | 配置入口 |
| Agent 循环、工具调用、基础重试 | Pi durable | 与长任务相关的策略和配置 |
| 会话、持久任务、检查点、崩溃恢复 | Pi durable、其 SQLite 等存储适配 | 业务目标和进度，不复制会话或任务引擎 |
| 上下文压缩与交接 | Pi compaction、reset/handoff 接口 | 合适的触发配置和必要的交接信息 |
| 子 Agent | Pi 多会话、任务归属、等待与取消 | 薄的委派接口、简短结果和并发策略 |
| 终端与文件操作 | Pi 原生工具与本地 Environment | 必要的目录、权限和调用适配 |
| 用量与成本统计 | Pi usage | 任务级限制和清楚的进度展示 |
| computer-use | 现有驱动及其工具接口 | 工具适配、共享桌面占用和中断后的状态核对 |
| 联网、平台访问、Skills | 供应商现有能力、现成工具与 Skill 入口 | 必要的接入；不把渠道建设变成项目主线 |

“Pi 有机制”不代表本项目已正确接入；配置和接入应先于自建替代实现。基础重试与“任务没有完成，选择下一步继续”是不同层次，后者才是本项目需要补充的策略。

## 3. 核心范围

### 3.1 持续推进一个目标

- 业务状态保持最小：目标、当前进度、下一步、交付物、完成条件和阻塞原因。
- 状态存入 Pi 提供的持久机制，不另建任务数据库或通用工作流引擎。
- 使用 Pi 已有扩展点，在执行边界判断继续、验证、完成或阻塞。模型一轮答复结束不自动等于目标完成。
- 复用 Pi 的压缩与恢复能力，配置适合本地长任务的策略；不重新实现压缩器、调度器或重放机制。
- 使用 Pi usage 执行一次配置的任务预算。内部 token 统计阈值不能默认变成反复要求用户继续的节点。

### 3.2 衔接本地执行步骤

- 优先接通 Pi 原生终端和文件能力，让同一个目标可以连续执行本地命令、处理文件并操作应用。
- computer-use 直接接现成驱动，不自研截图、鼠标、键盘或浏览器自动化引擎。
- 多 Agent 可处理独立工作；对同一个共享桌面，按必要流程协调占用，避免依赖窗口焦点的操作交错。
- 中断后依据 Pi 保存的执行记录检查当前文件或应用状态，再继续。不能把恢复会话视为外部操作从未发生，也不能盲目重复有副作用的动作。

### 3.3 按任务检查交付

- 验证与用户目标相关：本地脚本/测试、文件内容、应用最终状态，或必要时的模型评审。
- 优先使用便宜、直接的检查。独立评审 Agent 是可选手段，不是每个任务的固定成本。
- 未满足条件时给出具体证据并继续修正；恢复策略耗尽或遇到真实阻塞时保留原因。
- 不建设通用评审平台、统一行业证据系统或庞大的任务协议。
- 研究任务要求查资料时，检查实际检索与引用；这是该类任务的验收要求，不强加给其他任务。

## 4. 技术与实现颗粒度

一个目标对应一次任务运行，内部直接复用 Pi 会话、工具与检查点。实现优先采用 Pi extension、hook、原生工具和配置；只有上游缺少必要接口时才增加薄适配。

```text
最小 CLI / 现有交互入口
          ↓
本项目：长任务推进策略 + 本地执行协调 + 按任务验证
          ↓
Pi：模型、循环、工具执行、会话、压缩、持久化与恢复
          ↓
Pi 终端/文件工具 · 现成 computer-use 驱动 · 按需工具和 Skills
```

基础执行机制只有 Pi 一套。已有本地后台服务和 HTTP 接口先作为原型入口保留，不扩成对外平台；后续仅在后台运行和恢复确有需要时保留最薄宿主。

## 5. 明确排除

- 自研 Agent runtime、调度引擎、存储引擎、模型网关和通用工作流框架。
- 分布式 Agent 集群、消息总线、云端控制面和多租户管理。
- 自研电脑驱动、浏览器引擎、搜索引擎和完整记忆平台。
- 为展示能力而固定堆叠规划、执行、评审等多个 Agent。
- 大量平台渠道接入、复杂 UI、插件市场及社区运营功能。

只有真实案例证明属于本地长任务缺口，且 Pi/现成工具无法覆盖的部分，才进入实现范围。

## 6. 当前原型的取舍

现有代码和历史任务保留。v0.3 新任务已接通原生执行、预算与可选评审；旧任务保留保存时的工具与预算语义。

| 当前部分 | 决策 |
|---|---|
| Pi AI、Pi durable、Pi 存储接入 | 保留，明确能力归属 |
| `runtime.ts` | 收敛为 Pi 生命周期薄封装与目标推进策略，避免继续叠加基础设施 |
| `goal.ts`、`checks.ts` | 保留必要业务目标和完成检查，简化固定协议，评审按需启用 |
| `delegation.ts` | 保留薄委派，复用 Pi 会话；先不建设完整 Agent 消息体系 |
| `workspace.ts` | 审查哪些工具可由 Pi 原生工具替代，只保留必要边界适配 |
| `computer.ts` | 保留薄驱动适配，补真实流程需要的占用与状态核对 |
| CLI、聊天、本地服务 | 保留最小可用入口，不继续扩展平台功能 |
| DeepSeek 联网、Agent Reach | 作为现成能力接入，不成为自建检索基础设施 |

当前优先级：用终端真实案例和原生 Pi 对照验证连续推进的收益。电脑执行方式与驱动选型尚待用户确认；默认关闭，不继续 CuaDriver 授权与桌面联调。

## 7. 验证项目增量

基线为原生 Pi，使用同一版本、模型、执行工具和权限；对照组只增加本项目的长任务策略与本地协调，不能靠更强模型或额外工具制造优势。

先固定少量真实案例：终端完成文件/数据处理任务、桌面应用完成明确操作流程、终端与应用混合的资料处理任务。包含任务中断、网络暂时失败、子任务失败及交付检查不通过的情况。

比较：完成率、用户介入次数、中断后恢复表现、重复执行情况、总耗时和每个完成任务的成本。每新增模块都应回答：它改善了哪个指标，Pi 是否已有可复用实现。

用户只提交一次目标，在事先配置的总预算内，无需反复“继续”仍能完成，是关键验收项。登录、缺必要信息或真实硬预算用尽等确需介入的情况应单独记录。

先证明这些增量，再发布开源项目。不以更多功能、Agent 数量或运行时间作为效果证明。

## 8. 已实现与验证状态

v0.3 首轮实现：

- 原生执行：复用 Pi `createCodingTools/createBashTool/NodeExecutionEnv`；实际执行命令、分段读取、写入和编辑。命令不自动继承供应商凭据；本地执行没有 OS 沙箱。
- 持续推进：保留最小目标状态与检查不通过后的继续策略；复用 Pi 后台压缩，默认约 48k 当前上下文开始准备摘要。新任务取消默认累计 500k token 硬停，改用费用/总时限，可显式配置 token 限制。
- 按需成本：不固定创建子 Agent 或独立评审。用 Pi usage 统计任务估算费用，硬预算真实用尽时仍需显式补充。
- 真实联网：薄接 DeepSeek 官方 Search/Fetch 及已安装的 Agent Reach；明确研究任务检查访问与引用记录，不把这个检查等同于逐条事实验证。
- 可选电脑接口：通用 MCP 桥接具备流程占用、过期后重新观察和释放。仅模拟桌面验证；真实驱动关闭，未通过桌面验收。

35 项自动测试通过，覆盖原生 Shell 的执行/暂停取消、文件工具、Pi 压缩、旧任务兼容、联网证据、费用限制持久化，以及原有委派/评审/返工强杀恢复等。真实 DeepSeek 联调通过错误交付自动修正、两个子 Agent 计算与报告、实际联网正文读取和终端检查，全程无续跑消息。

同模型、同终端工具单案例对照中，原生 Pi 和本扩展均成功，本扩展更慢、更贵；这表明新增策略有开销，尚不能证明通用长任务收益。尚待验证：更广泛的长任务完成率、长时间连续运行与真实桌面/混合流程。详细结果见 [验证记录](../verification-2026-10-30.md)。

此前的完整 Spec、线上联调记录说明及较宽的 v0.3 探索稿移至 [历史文档](SPEC-exploration-2026-10-30.md)。它们用于追溯实验，不作为当前实施范围；本文件的范围约束优先。

### 8.1 三组真实任务对照后的取舍

2026-10-30 对同一 OWID/IEA 研究交付任务比较 Pi SDK 加共同工具、Pi 加 Goal-Driven 初始用户模板、当前实现；模型、根工具 schema、材料、预算和压缩配置一致。三组主要计算与新目录重建均通过，人工后续消息均为 0，但报告都含实质错误，不能称为全部完成。当前实现较基线多 25.6% 累计 token、18.3% 时间，缓存后费用接近；一次自动返工主要补登记计划，没有发现独立验收找出的缺陷。尚未证明新增策略提升长任务质量。详见 [完整结果与限制](../experiments/2026-10-30-long-task-results.md)。

后续收敛决策：继续复用 Pi；保留最小目标/验收状态、费用/时限与按需委派；简化强制 checkpoint 登记，以实际交付条件判断完成；只在具体失败证据下自动返工；优先补任务相关的验证，不扩展运行基础设施。独立评审和真实桌面尚未在此对照中验证。这些是后续修改方向，本轮没有改变生产执行行为。
