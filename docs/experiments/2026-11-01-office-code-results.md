## 检查器纠正与额外审计

v1 用“移除监听器次数等于添加次数”检查清理，误报了当前组第一次并发实现的幂等重复清理。重复移除不会留下监听器，因此这条判据过严。原始 v1 结果没有覆盖；对四份并发产物统一改用实际残留监听器检查，纠正后的同覆盖复核全部通过。

随后统一增加两条行为探针：三个 worker 同时运行时，一个失败、另一个成功，仍须等待最后一个结束；`null/undefined/0/false/空字符串` 的拒绝原因必须保持为失败。Pi 第一次在 `null` 拒绝时误判为成功；当前第一次在另一个 worker 尚未完成时提前结束。两组第二次均通过。补充探针没有反馈给执行模型，也没有重写产物或追加付费执行。

当前默认检查器采用 v2，并用参考解、无害的重复清理实现以及真实监听器泄漏、提前结束和假值拒绝缺陷重新校准：8 个参考解通过、19 个故意错误被拒绝、重复清理仍通过。首次冻结版为 16 个故意错误；[检查器差异](2026-11-01-pool-checker-correction.patch)保留这次变化，CSV 同时保留三个口径。

执行轨迹另显示：Pi 第一次资料交接对全部输入运行哈希，读到了明确排除的内容。它的最终 ZIP 通过自动检查，不能据此宣称执行范围也合格。该发现没有偷偷并入冻结输出分数；它再次说明输出检查不能证明此前访问过哪些文件。事后直接 Python 文件读取探针发现 Pi 第二次构建器会读取 context.txt，但这个探针不是 OS 沙箱，也不能证明没有其他访问。

4 份 DOCX、4 份 XLSX 全部渲染并查看，共 15 页。Word 均为 1–2 页，未发现缺字、内容裁切；当前第一次 Word 的来源标题与正文跨页，需改善分页。Excel 单页签全部列已检查，诊断打印默认把列拆成两页，XLSX 的数据类型检查独立保留。这些版式观察不覆盖业务错误，也未用于修补产物。

## 实际结论与下一轮

本轮能够检验短任务的实际交付和检查缺口。两组人工请求都是零，监督返工都是零，不能归因出目标持续推进策略的介入收益；Skill 未被读取，不能归因出复用收益。预设的共同 brief 只绑定公开命令，这轮也不检验准备阶段能否把语义要求拆成更充分的标准。

先把会议状态合并、客户字段保留、文件范围和并发失败这些缺陷沉淀为任务可调用的原生 Skill 检查，再做包含重启、恢复和连续多步骤的小时级真实办公/编程任务。本轮最长约 79 秒，未验证长时间运行的可靠性。版式渲染曾与其他案例并行进行，主机负载未控制，不作速度优劣结论。

复现先运行 `npm run test:cases`；`npm run test:compare:cases` 只准备，显式加 `--execute` 才调用模型。默认现在使用 v2 判据，不能与 v1 原始列混用。私有完整记录位于 `.harness/office-code-studies/a41c8362-9ece-4426-bd08-4c4c59f983d3`，包含冻结版源码、会话、原始结果、补充结果和渲染；不提交密钥、个人资料或原始会话。

收尾验证：`npm run check` 的 113 项测试全部通过、无跳过，类型检查与构建通过；新增对照脚本单独类型检查通过；`npm audit --audit-level=moderate` 为零漏洞。案例自检在 Python3.9 与3.12均通过，按任务契约核对原始文件，避免把Python3.12生成的字节码缓存误认成改写原测试。最新便携性修正后又单跑8项案例测试通过。Linux/macOS CI 已配置 Python3.12 及开发用办公依赖，远端尚未执行；本轮未改桌面UI，因此未重复桌面交互测试。
