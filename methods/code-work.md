# 修改已有代码并交付

1. 先读用户要求、项目说明、原有测试和支持的运行环境。列出允许修改的文件和必须保持的行为。优先复用项目既有测试，不默认安装依赖、升级框架或重建运行环境。
2. 对已经存在的项目测试或用户提供的核对程序，在任务说明的命令型标准中记录 `verification: {command, inputs, outputs}`。命令与原始核对输入在确认后固定。inputs 放需要保持原样的测试/基准材料；待修改源码是 outputs，不放进不可修改的 inputs。新增自测另行运行，不替代原始检查。
3. 根据缺陷检查原行为和兼容边界：合法空值、真实零、嵌套输入、错误输入、顺序/重复、导出与类型、已有接口。针对变更测试；不能只跑新功能的正例。涉及类型时同时检查应接受和应拒绝的输入，避免靠 any 扩宽伪造通过。
4. 用 Pi 原生工具修改，在 task_verify 中实际运行约定命令，绑定核对程序、有关输入和整个待交付源码/目录。命令退出0只证明实际执行的检查；测试有没有覆盖关键要求需要说明。修改源码、测试或目录内容后重新核验。
5. 交付实际代码目录、简短变更说明、复现/测试命令和真实未覆盖范围。未运行上游完整工具链或旧环境就明确写出。不要把模型写的 passed 或测试数量当作兼容性证明。

常规修复和阶段切换由 Agent 在确认预算内完成；真实信息/授权缺失或预算耗尽时保留现场。中断后先看实际文件、进程及 Pi 任务状态，避免重复已生效的动作。
